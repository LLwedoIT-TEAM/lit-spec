# Publishing workflow

This workflow is illustrative. Teams may adapt it while preserving the conformance requirements.

## 1. Initialize

Create the five manifests. Assign a stable project URI and IDs for contributors and initial components. Record the intended LIT version in every manifest.

## 2. Draft and assemble

Store prose inline for small excerpts or by `href` for ordinary manuscripts. Add components as chapters, poems, essays, branches, or other units. Use `sequence` for a single reading order and relationships for alternatives or cross-references.

## 3. Curate canon

Record facts that tools and collaborators need to preserve. Mark unresolved claims as `provisional`, `disputed`, or `ambiguous`. Link assertions to the components that provide evidence.

## 4. Record provenance

Append an activity when material is created, imported, translated, generated, or substantially revised. Identify both tools and accountable people. Avoid confidential workflow data in bundles intended for publication.

## 5. Clear rights

Confirm rights holders and grants for every distributed asset. Set explicit AI-use signals when known. Have qualified counsel review legal terms for consequential releases; the manifest does not replace an agreement.

## 6. Validate

Validate JSON syntax and schemas, then run bundle-level checks for unique IDs, resolvable references, consistent versions, integrity digests, and rights coverage.

## 7. Package and release

Publish manifests beside their referenced content or use stable absolute URIs. Preserve relative paths when moving a self-contained bundle. Tag the release, record the LIT version, and retain the exact published manifests for auditability.

## 8. Revise

Treat published metadata as history. Append provenance activities, update changed grants, and mark superseded canon assertions `retconned` rather than erasing meaningful prior states. Increment the project release according to its own versioning policy.
